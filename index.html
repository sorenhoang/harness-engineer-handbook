Understanding Harness Engineering

From agent loops and tool interfaces to context, sandboxes, verification, and long-running work. A short technical handbook for AI engineers, developers, and serious learners.

Original author: @techNmak43 sections+ Part IX: source checks & best practices
Orientation

What this handbook will make clear

00

What this handbook will make clear

A capable language model is not, by itself, a working agent.

Something has to decide what the model sees, expose the actions it can take, execute those actions, return observations, preserve useful state, enforce permissions, recover after failure, decide whether another step is needed, and determine whether the task actually succeeded.

That surrounding machinery is increasingly described as an agent harness.

The terminology is still young. Microsoft currently uses agent harness for runtime scaffolding that turns a language model into an agent by coordinating model calls, tool calls, context, state, approvals, and multi-step execution [15]. Anthropic uses a closely related runtime meaning when it separates a durable session, a harness that runs the model/tool loop, and a sandbox that executes code [12]. OpenAI uses harness engineering more broadly for the engineering of environments, feedback loops, repository structure, constraints, observability, and other scaffolding required for reliable agentic work [10].

For this handbook, we will use the following working distinction:

  • Agent harness: the runtime and control machinery immediately surrounding a model and allowing it to act over multiple steps.
  • Harness engineering: the broader engineering discipline of designing the interfaces, context policy, state, execution environment, controls, feedback systems, recovery behavior, and verification mechanisms that make agentic work reliable.

This is an editorial taxonomy for this handbook, not an industry-standard definition.

By the end, you should be able to explain:

  • why a model call is not yet an agent;
  • how a minimal agent loop works;
  • how the model, harness, session, tools, and sandbox differ;
  • why tool design changes agent behavior;
  • why MCP is useful but does not specify a complete agent architecture;
  • why active context is different from durable state;
  • why compaction is lossy;
  • how permissions, containment, credentials, and approvals solve different problems;
  • why tool failures need model-usable error semantics;
  • why retries become dangerous around non-idempotent side effects;
  • why verification should be separated from self-reported completion;
  • how long-running agents inherit familiar durability and consistency problems;
  • when subagents help and when coordination costs dominate;
  • how evaluation measures the model and the harness together;
  • why harness assumptions should be retested as models improve.

Prerequisites: basic familiarity with language-model inference, function/tool calling, context windows, and ordinary software systems is enough.

Scope: this is a handbook about the systems layer around agentic model execution. It is not a complete MCP handbook, agent-security textbook, distributed-systems textbook, or catalog of every agent framework.

Part I

Foundations: model, loop, and harness

01

A model call is not an agent

A language-model invocation can be written abstractly as

y ~ p_θ( · | c )

where c is the context supplied to the model and y is the generated output.

Nothing in that expression automatically means that a shell command runs, a browser opens, a file changes, an API call is retried, a failed attempt is observed, or work continues after the first response.

An agentic system adds an external control process around model inference. A useful conceptual decomposition is:

agent system ≈ model + harness + environment

This is not a formal identity. It is a mental model.

The model supplies learned capability. The harness decides how inference is connected to actions and repeated over time. The environment contains the external state that actions inspect or modify.

Anthropic distinguishes ordinary workflows, whose execution paths are substantially specified by application code, from agents, where the model dynamically chooses actions and strategies [4]. Microsoft similarly distinguishes ordinary agents, workflows, and a harness agent assembled for longer multi-step work [15].

Key idea

The important boundary is not “chatbot versus agent” as a marketing label. It is whether model output participates in a controlled interaction loop with external state.

02

The minimal agent loop

A harness can be described with four evolving objects. Let:

  • s_t = durable or working state before step t
  • c_t = G(s_t) = the context selected for the next model call
  • a_t = M(c_t) = the model output, which may include an action request
  • o_t = E(a_t) = the observation produced by the environment if an action executes

The harness then updates state:

s_(t+1) = U(s_t, a_t, o_t)

This formalization is ours; it is not a standard API. The loop is:

A modern runner usually performs some variation of this loop: call the model, inspect the response, return if it is final, execute tools if requested, append results, then call the model again [14].

ReAct is an important research predecessor. It studied language-model trajectories in which reasoning and task actions are interleaved so that external observations can affect later decisions [1]. Modern harnesses do not need to expose or persist private reasoning traces to retain the durable systems idea:

Key idea

act → observe → update → continue.

03

What the harness actually controls

The word “harness” becomes useful when we list the responsibilities that do not belong to the model weights. A harness may decide:

  • which instructions and state enter the next context;
  • which tools are visible;
  • how tool schemas are represented;
  • whether a tool call is permitted;
  • whether human approval is required;
  • how the tool executes;
  • how tool results are transformed before returning to the model;
  • how history is persisted;
  • how context is compacted;
  • when subagents are created;
  • how errors are returned;
  • how retries are handled;
  • what budgets terminate a run;
  • what evidence is required before accepting completion;
  • how traces and metrics are recorded;
  • how execution resumes after interruption.

Not every harness owns all of these concerns. Some systems delegate state, execution, policy, or recovery to other components.

That is why “harness” is best treated as a control-plane concept rather than a synonym for one library or process.

OpenAI’s current Agents API, for example, manages sessions, orchestration, context compaction, and recovery while allowing the application to choose tools and an execution environment [14]. Microsoft’s Harness composes chat clients, context providers, persistence, compaction, approvals, observability, and bounded looping [15].

These examples are implementation snapshots, not permanent definitions. As of this handbook’s publication, OpenAI’s Agents API is in public beta. Microsoft’s packaged Harness factory is released, while background agents, file access, and looping are still marked experimental, and its shell tooling is pre-release.

04

Model, harness, session, tool, and sandbox

These terms describe different system objects.

TermUseful meaning
ModelThe learned inference system
AgentThe model operating within an action loop toward a task
HarnessRuntime/control machinery driving that loop
SessionLogical history/state container for ongoing work; durability depends on the implementation
ContextInformation supplied to a particular model invocation
ToolA callable capability exposed to the model
SandboxA controlled execution environment
WorkflowAn execution structure largely specified by code
Evaluation harnessInfrastructure that runs and grades evaluations

Anthropic’s Managed Agents architecture explicitly separates session, harness, and sandbox. The session is an append-only log, the harness invokes the model and routes tool calls, and the sandbox runs code and edits files [12].

OpenAI makes a related distinction in its sandbox architecture: the harness is the control plane around model calls, routing, approvals, tracing, recovery, and run state; the sandbox is the execution plane that reads and writes files, runs commands, installs dependencies, and snapshots state [14].

The boundaries can be implemented differently. The conceptual separation remains useful because the components fail differently and carry different trust assumptions.

Part II

Tools and the agent-computer interface

05

An agent-computer interface

A model never interacts with “the computer” in the abstract. It interacts with an interface.

One coding harness might expose:

read_file(path, start_line, end_line)
search_code(query)
apply_patch(path, patch)
run_tests(target)

Another might expose only:

shell(command)

Both may eventually manipulate the same repository. They do not present the same problem to the model.

SWE-agent formalized this idea as the Agent-Computer Interface (ACI). Instead of assuming that interfaces built for human developers are automatically optimal for language models, the work treats interface design itself as an experimental variable. The authors designed repository-navigation, editing, testing, and feedback mechanisms around agent behavior, then measured how those choices affected performance [2].

Their original paper reported 12.5% pass@1 on SWE-bench and 87.7% on HumanEvalFix for the evaluated SWE-agent setup [2]. These numbers are historical results for the paper’s models, harness, tasks, and evaluation procedure. They are not universal claims about ACI design.

The engineering question

Is the capability merely available, or is it exposed in a form the model can use reliably?

06

Affordance, contract, observation, feedback

A useful way to analyze any agent-facing tool is through four properties:

  • Affordance. What operation can the tool perform?
  • Contract. How does the model request the operation?
  • Observation. What information comes back?
  • Feedback. Does the result make the next correct action easier?

Consider file editing. A raw shell gives enormous affordance. It also forces the model to select commands, quote paths correctly, infer tool output, and recover from formatting mistakes.

A structured patch tool narrows the action surface but may make intent easier to express and outcomes easier to verify.

Neither interface is universally superior. The correct design depends on the model, task, environment, and evaluation.

Key idea

Interface structure becomes part of the effective difficulty of the task [2,5].

07

Tools are part of the model input

A tool is not only executable code. Its name, description, arguments, and result representation are usually placed into the model’s context.

That means tool design affects inference before a tool is ever called.

Anthropic frames tool design as an interface problem between conventional software and probabilistic agent behavior. Their engineering work emphasizes clear purpose, unambiguous parameters, namespacing, useful response content, and token-efficient results [5].

Two costs are useful to separate:

C_tool = C_selection + C_observation

This is a conceptual decomposition. C_selection is the difficulty of choosing the correct tool and arguments. C_observation is the context and reasoning burden imposed by the returned result.

A tool with an elegant backend API can still be poor for an agent if its descriptions overlap with other tools or its results dump irrelevant data into the context window.

08

More tools can make the decision harder

A system might expose six nearly overlapping operations:

search()   find()   lookup()   query()   grep()   retrieve()

From a traditional capability perspective, this looks rich. From the model’s perspective, every additional tool adds another choice to the action space.

Anthropic reports a common failure mode in which bloated or overlapping tool sets create ambiguous decision points. Their tool-design guidance recommends selecting a smaller number of distinct operations where possible, using namespacing to separate related capabilities, and evaluating naming schemes rather than assuming one universal convention [5].

Production rule

Tool count is not a monotonic measure of agent capability.

Adding a tool can improve reachable behavior while simultaneously making tool selection more difficult. That trade-off should be measured on representative tasks rather than settled by aesthetics.

09

Tool results should return high-signal context

Suppose an agent asks for a customer record. A low-level API might return hundreds of fields, internal identifiers, pagination metadata, image variants, audit records, and storage keys.

A human-written program can cheaply ignore fields. A language model must consume returned text through its context budget.

Anthropic recommends returning high-signal information, using filters and pagination for potentially large results, and exposing concise versus detailed modes where appropriate [5,6]. The exact best format can vary by task and model.

This means a tool result should be judged by more than correctness. Ask:

  • Did it return the information needed for the next decision?
  • Did it omit irrelevant payload?
  • Did it preserve identifiers required for later actions?
  • Did truncation explain how to retrieve more?
  • Did the format make the result easy to interpret?
Key idea

Tool output is part of context engineering.

10

Tool errors are observations too

A tool failure can terminate the run, trigger an automatic retry, or return a model-visible error and allow recovery. Those semantics are different.

Imagine:

deploy_service(environment="prod")

fails because the requested branch does not exist. An opaque result such as:

Error.

forces the model to guess. A more useful result might provide:

status: failed
reason: branch_not_found
requested_branch: release/2.4
available_branches: [...]
side_effects: none
retryable: true

The exact schema is application-specific. The general principle is not.

OpenAI’s current Agents SDK distinguishes two cases. Setting toolNotFoundBehavior to return_error_to_model can turn an unresolved function-tool call into a model-visible error so the run continues; separately, toolErrorFormatter customizes tool error messages returned to the model [14]. Anthropic likewise recommends actionable validation errors over opaque codes or raw tracebacks [5].

Key idea

A recoverable failure should give the model enough information to choose a better next action without pretending the failed operation succeeded.

11

MCP is an interoperability layer, not a complete agent loop

The Model Context Protocol standardizes interfaces between AI applications and external capabilities.

The dated MCP core server specification centers server primitives such as prompts, resources, and tools. Tasks is a separate opt-in MCP extension, not part of the core protocol. At publication time, first-party MCP surfaces describe its maturity inconsistently: the MCP extensions overview lists MCP Tasks among official extension repositories, while the ext-tasks repository README labels the repository experimental and not official, and the published Tasks specification page is marked Draft. Because those first-party labels conflict, this handbook treats Tasks as an evolving optional extension rather than assigning it a single maturity status [13].

The current published Tasks draft allows a server to return an asynchronous task handle for a tools/call and defines tasks/get, tasks/update, and tasks/cancel. It advises clients to persist task IDs to durable storage so polling can resume after a crash or restart. Task support is negotiated explicitly, and host support can vary [13].

This makes MCP increasingly capable, but an important boundary remains. MCP does not, by itself, determine:

  • how the model loop is scheduled;
  • how active context is selected;
  • how a task is judged complete;
  • which actions require approval;
  • how side effects are retried;
  • how a sandbox is provisioned;
  • how multiple agents coordinate;
  • how the overall agent is evaluated.

A harness may use MCP heavily while still owning those policies elsewhere. Conceptually:

Safe mental model

Interoperable capability interface, not entire agent architecture.

The current Tasks draft also illustrates why protocol state and tool outcome should not be collapsed. A tool result with isError: true still completes the task at the protocol level, while JSON-RPC execution errors use the task’s failed state [13]. That distinction is useful when designing model-visible error handling and recovery.

Part III

Context, state, and memory

12

Active context is a harness decision

Every model call sees a finite context. The harness determines what enters it. Potential ingredients include:

  • system and developer instructions;
  • the current user task;
  • recent message history;
  • tool schemas;
  • tool results;
  • retrieved documentation;
  • plans and todo state;
  • summaries of earlier work;
  • file or repository state;
  • memory records;
  • outputs from subagents.

A naive policy is to include everything that might ever matter. That eventually fails for two reasons.

First, context capacity is finite.

Second, relevance matters even when capacity is large. Irrelevant material competes with useful evidence for model attention and can make the decision problem harder.

Anthropic’s context-engineering guidance therefore treats context as a constrained resource and emphasizes just-in-time retrieval, token-efficient tools, compaction, structured memory, and subagents [6].

13

Progressive disclosure instead of monolithic instructions

OpenAI’s Codex-first engineering experiment encountered a practical documentation problem. A large repository instruction file accumulated too much guidance. It consumed context, became difficult to maintain, and was hard to verify mechanically.

The team moved toward a shorter entry-point document that pointed agents to structured repository-local sources of truth [10].

The general pattern is progressive disclosure:

  1. provide enough information to orient the agent;
  2. make deeper information discoverable;
  3. load detailed guidance only when the task requires it.

This is the same reason tool interfaces benefit from search, filters, and concise result modes. Availability and relevance are different properties.

Key idea

A large context window does not make an undifferentiated information dump a good architecture.

Agent Skills are another modern use of progressive disclosure. Anthropic and Microsoft describe skills as reusable packages of instructions and optional scripts/resources that can be discovered and loaded when relevant instead of placing all guidance in every prompt [25,26]. Unlike a tool, whose primary interface is a callable action, a skill primarily packages reusable guidance and supporting resources that the model can draw on while deciding how to work.

Microsoft distinguishes this from an explicit workflow, where the execution path is defined by the application; its current guidance prefers workflows when checkpointing, predictable ordering, or non-idempotent side effects make replaying a flexible skill undesirable [26].

A 2026 preprint analyzes 307 confirmed skill-induced failures across SkillsBench and SWE-Skills-Bench, including 125 functional failures and 182 efficiency regressions [24]. That study attributes selected paired failures or cost regressions to loaded skills; it does not estimate a general base rate for how often skills fail across arbitrary deployments. Skills should therefore be evaluated rather than assumed beneficial. Because skills may contain instructions, resources, and executable scripts, their provenance is also a security concern; Section 22 returns to that boundary.

Source checkMicrosoft’s docs say workflows are most useful when you need “guaranteed execution order” and resume from the last checkpoint. The phrase “non-idempotent side effects” is the handbook author’s gloss; it does not appear in the Microsoft documentation.
14

Durable history and active context are different state surfaces

A long-running task can have more history than any one inference call should see. This makes the distinction between durable session state and active model context fundamental.

Anthropic’s Managed Agents design stores an append-only session log outside the active context window. The harness can retrieve slices of that history and transform them before passing selected information back to the model [12].

OpenAI’s Agents API similarly separates a durable session from the context-management behavior performed by the managed harness [14].

The two state surfaces overlap, but neither generally contains the other. Durable history can remain outside the next model call, while active context can also contain ephemeral material such as the current user message, live tool schemas, or temporary runtime metadata that was never stored in the durable session.

The exact storage model differs by product. The principle is broader:

Key idea

Persistent availability does not imply automatic inclusion in every inference call, and inclusion in one inference call does not imply durable storage.

15

Compaction is lossy

When a conversation grows too large, a common strategy is to replace older detail with a shorter summary. This reduces active-context cost. It can also lose information.

Let H be a history and C(H) a compacted representation. In general:

C(H) ≠ H

The transformation cannot be assumed to preserve every detail future steps may need.

Anthropic explicitly warns that context-retention decisions can create failures because future turns may require information that seemed unimportant earlier. Their Managed Agents architecture therefore keeps durable session history separately from the compacted context seen by the model [6,12].

Compaction should be understood as context transformation, not equivalent to deleting durable history.

The engineering question

Which information can be summarized, which should remain directly recoverable, and how can the agent retrieve omitted detail later?

16

Case study: harness changes can alter agent quality

A useful real-world example came from Anthropic’s April 2026 Claude Code postmortem [19].

Anthropic reported that its API and inference layer were unaffected, while three product-layer changes changed the quality users experienced in Claude Code and related products:

  • the default reasoning-effort setting was reduced for some models and later reverted after user feedback;
  • a session optimization intended to clear older reasoning after an idle period contained a bug that repeated the clearing behavior on later turns, making Claude appear forgetful and repetitive;
  • a system-prompt instruction intended to reduce verbosity produced a 3% drop on one broader evaluation for both Opus 4.6 and Opus 4.7, and was reverted [19].

The point is not that these three mechanisms are universally important. The point is architectural:

Key idea

Observed agent quality can change when the product/harness configuration changes even when the underlying API and inference layer have not changed.

Prompt construction, reasoning settings, context retention, tool interfaces, and other runtime decisions are therefore part of the behavior of the deployed agent system.

17

Structured working state

Natural-language history is not the only way to preserve progress. Long tasks often benefit from explicit artifacts such as:

  • todo lists;
  • issue trackers;
  • feature status files;
  • progress notes;
  • test results;
  • git commits;
  • checklists;
  • generated plans;
  • output manifests.

Anthropic’s long-running-agent experiments used an initializer session to prepare structured artifacts and later coding sessions to make incremental progress while leaving clear state for the next session [7]. Their example used feature lists, git history, progress notes, and an initialization script.

These artifacts are not hidden model memory. They are external representations of task state.

Key idea

That makes them inspectable, editable, versionable, and recoverable by future sessions or humans.

Part IV

Execution environments and security

18

Execution environments

Some agents only read data. Others run code, modify files, browse web applications, compile software, invoke internal systems, or create persistent artifacts.

Once an agent can cause side effects, the execution environment becomes part of the architecture. A sandbox may provide:

  • filesystem access;
  • shell execution;
  • installed packages;
  • mounted data;
  • network access;
  • browser or computer control;
  • ports;
  • snapshots;
  • resource limits.

OpenAI’s sandbox documentation explicitly separates this execution plane from the harness control plane [14].

The environment determines both capability and failure mode. A correct plan can fail because a package is missing. A poorly constrained environment can succeed while creating an unacceptable security risk.

Key idea

Harness engineering therefore cannot stop at prompt design.

19

A sandbox is an isolation boundary, not the orchestrator

Is outbound networking allowed?Does this call require approval?
What credentials or mounts are visible?What result should be returned?

The two can be colocated in a prototype. They should still be reasoned about separately.

Key idea

Keeping the control plane outside untrusted execution can protect session state, audit logs, credentials, and policy from model-generated code running inside the sandbox [12,14].

20

Approval and containment solve different problems

Human approval can be valuable when an action has consequences that should remain under explicit human control. Examples include deleting production data, sending external communication, transferring money, escalating privileges, or publishing changes.

But approval is not a complete security architecture.

Anthropic reports that users approved roughly 93% of Claude Code permission prompts in the telemetry discussed in its containment article [3]. That is Anthropic-specific product telemetry, not a universal approval rate. Their argument is that frequent prompts can create approval fatigue.

The same article gives a more extreme internal red-team example. In a controlled February 2026 exercise, a malicious prompt delivered through the user successfully exfiltrated credentials in 24 of 25 retries [3]. Anthropic’s conclusion for that scenario was that environment-level filesystem and egress boundaries were the defense that held when model-layer intent checks could not distinguish the malicious instruction from an ordinary user request. This is a vendor-reported red-team result, not a general failure rate.

Containment addresses a different question:

The containment question

What can the agent reach even if every higher-level behavioral safeguard fails?

Examples include filesystem boundaries, network egress rules, VMs, containers, and credential isolation.

Source checkIn the red-team exercise the exfiltration succeeded (24 of 25 retries). The original article concludes that only the environment (egress controls, a filesystem boundary keeping ~/.aws out of reach) could stop this kind of attack. No defense “held” in that exercise. The exfiltration through an approved domain was a separate incident involving Cowork.

Human review controls decisions. Containment controls reachable capability.

21

Keep credentials out of untrusted execution

Suppose model-generated code runs inside a sandbox that also contains long-lived credentials. Then a prompt injection, malicious dependency, or incorrect command may be able to read those secrets.

Anthropic describes a structural alternative in Managed Agents: credentials can live outside the execution sandbox and be used through controlled proxies or resource-specific mechanisms rather than being exposed directly to generated code [12].

Their containment work makes the general security principle clear [3]:

Key idea

A resource that never enters the sandbox cannot be read directly from that sandbox.

This is a stronger boundary than telling the model not to access secrets. One is an instruction. The other changes the reachable state space.

22

Observations have provenance

Agent input does not only come from the user. A harness may place into context:

  • web pages; emails; issue descriptions; documents; files;
  • database records; MCP resources;
  • loaded skill instructions and resources;
  • tool results; subagent reports; stored memory.

Those observations may contain hostile or misleading instructions. A useful conceptual representation is:

o_i = (content, source, trust, time, permissions)

This is our mental model, not a standard wire format. The point is that all strings are not equal merely because they become tokens. A system instruction and text scraped from an arbitrary website can both enter model context while having very different provenance and authority.

Anthropic’s containment work explicitly includes tools, files, and network access as external attack vectors and discusses persistent state as a new surface that can carry compromised information forward [3]. It also reports a concrete failure in which an approved network domain enabled data exfiltration through a legitimate API, leading Anthropic to treat an egress allowlist more like a capability grant than a simple destination filter. The same article warns that subagent output can create trust escalation if a parent agent treats it as inherently safer than raw tool output.

Independent research reaches the same broader security boundary from another direction. AgentDojo evaluates prompt injection against agents that operate over untrusted tool data; its initial NeurIPS 2024 release includes 97 realistic tasks and 629 security test cases across environments such as email, banking, travel, and messaging [21]. The benchmark exists precisely because data returned by tools can contain adversarial instructions that influence later agent actions.

Skills create a related trust boundary. Anthropic warns that skills can contain instructions and code and should be used only from trusted sources or audited carefully; a malicious skill can direct tool use or code execution in ways that do not match its stated purpose [25]. Microsoft likewise recommends treating skills like third-party code [26]. In its Agent Skills provider, load_skill, read_skill_resource, and run_skill_script require approval by default unless the application deliberately changes that policy for trusted sources.

Part V

Stopping conditions, budgets, and verification

23

Stopping conditions are part of the harness

An autonomous loop needs a rule for when to stop. Possible stopping conditions include:

  • the model returns a final output;
  • a verifiable task predicate is satisfied;
  • human input is required;
  • a guardrail blocks further action;
  • a tool enters a terminal failure;
  • a resource budget is exhausted;
  • a cancellation request arrives.

A production harness should distinguish completion from termination. For example:

task complete ≠ turn budget exhausted

OpenAI’s current Agents SDK supports explicit maximum-turn limits. Reaching that limit stops the loop but does not prove that the task succeeded [14]. Microsoft’s Harness similarly exposes bounded-loop behavior and configurable iteration limits [15].

Key idea

A stop can mean success, policy block, timeout, budget exhaustion, failure, or human handoff. Those states should not be collapsed into one generic “done.”

24

Budgets limit autonomy

A harness may enforce several independent budgets:

B = (B_turns, B_tokens, B_time, B_cost, B_tools, B_concurrency)

This vector is our conceptual notation. Not every platform exposes each budget directly.

The design point is that autonomy is bounded by resources as well as permissions.

  • A run can be allowed to call a database but still be limited to 20 tool calls.
  • A subagent system can be permitted while limiting concurrent workers.
  • A browser agent can be allowed to operate for ten minutes but not indefinitely.

Budgets turn “keep trying” from an unbounded behavior into an operational policy [14,15]. They also make failures easier to classify. A task that times out is different from a task that reaches a verified success condition.

25

Verification is different from self-reported completion

An agent can say:

The bug is fixed.

That is a claim. It is not evidence. For software work, stronger evidence might include:

  • the original reproduction no longer fails;
  • regression tests pass;
  • the application was exercised end-to-end;
  • the affected state changed as expected.

Anthropic’s long-running-agent work found that coding agents could mark features complete without adequate end-to-end testing. Their harness improved behavior by requiring explicit verification with browser automation and structured feature status [7].

Independent evaluation work makes the same distinction concrete. In τ-bench, success is evaluated by comparing the final database state with an annotated goal state rather than trusting the agent’s conversational claim. The benchmark also introduces pass^k to measure whether an agent succeeds consistently across repeated trials [22]. The conversational user in τ-bench is itself simulated by a language model, so the interaction trajectory is not deterministic even though the final environment state is compared with an annotated goal.

General principle

Whenever practical, completion should be tied to observable state outside the model’s own assertion.

For deterministic properties, deterministic verification is preferable. For subjective properties, a separate evaluator or human may still be useful.

26

This is a guideline, not a theorem.

OpenAI’s current Agents SDK provides input, output, and tool guardrails that can validate or block execution [14]. Anthropic’s containment work argues for environmental boundaries when the system can enforce hard reachability limits [3]. OpenAI’s Codex-first repository similarly moved some architectural rules from prose into linters and structural tests [10].

The model should not have to remember a rule that the system can cheaply enforce.

27

Generator and evaluator are different roles

Some outputs cannot be fully checked by a deterministic test. Examples include prose quality, design quality, research completeness, ambiguous planning, and certain forms of policy interpretation.

Anthropic experimented with separating generation from evaluation in long-running application work, using distinct roles to generate work, critique it, and iterate [11].

The useful concept is not that every task needs multiple agents. It is that producing an answer and judging an answer are different operations.

An evaluator can still be wrong. A model-based grader should therefore be treated as another fallible component whose own reliability needs evaluation. Where deterministic checks exist, they remain stronger.

28

Feedback loops give the agent external evidence

A one-shot model proposes output. An agent can often do something more useful:

  1. act;
  2. observe the consequence;
  3. revise.

For coding and operational work, useful feedback can include compiler output, unit tests, integration tests, screenshots, browser state, logs, metrics, traces, database contents, and API responses.

OpenAI’s harness-engineering report describes making application state, logs, metrics, and traces accessible to Codex so the agent could inspect and verify its own changes [10].

A tool that changes state but cannot expose the resulting state creates a weak feedback loop.

Key idea

Harness design is therefore partly about making relevant ground truth queryable.

Part VI

Long-running agents, recovery, and concurrency

29

Long-running agents inherit durability problems

A five-second tool call can often fail and be retried without much coordination. A task that lasts hours or days is different. During long-running work:

  • the harness can crash;
  • a worker can disappear;
  • a sandbox can be reclaimed;
  • the network can disconnect;
  • a user can pause the task;
  • approval can arrive hours later.

Google’s Agent Executor is explicitly designed around this operational problem, with event logs, snapshots, resumption, and distributed execution for agents, harnesses, tools, and sandboxes [16]. As of this handbook’s publication, Google’s google/ax repository warns that its core concepts, protocols, and specifications are still being refined and may change substantially before a stable release.

Anthropic’s Managed Agents architecture uses a durable session outside the harness so that a failed harness can be restarted and resume from the session log [12].

Key idea

As agent work becomes longer and more distributed, harnesses inherit familiar systems concerns: durability, recovery, consistency, retries, and failure isolation.

Backend note: this is the same problem a durable workflow engine (Temporal-style) or event sourcing solves. The append-only session log plays the role of the event log; the harness is a stateless worker that can die, be replaced, and replay the log to rebuild state.
30

Recovery requires control state and world state

Suppose a harness requests:

create_ticket(...)

The remote system creates the ticket. Then the network connection drops before the harness receives the response.

After restart, the harness knows it intended to call the tool. It may not know whether the external side effect committed. Blindly running the same action again can create a duplicate ticket.

This produces an important distinction:

requested action
executed action
observed result
committed task state

Those transitions do not necessarily fail atomically.

A durable event log helps the harness remember what it requested and observed [16]. It does not automatically make every external side effect safe to repeat [18].

Backend note: this is the classic dual-write and at-least-once delivery problem. Your log (control state) and the external system (world state) are two sources of truth with no shared transaction.
31

Idempotency matters for retries

An operation is idempotent, in the usual systems sense, when repeating the same intended operation has the same intended effect as performing it once [18]. Abstractly:

f(f(s)) = f(s)

For example, an operation such as:

set_ticket_status(id, "closed")

can often be designed to be idempotent. Operations such as:

charge_card(...)
send_email(...)
create_order(...)

are not naturally safe to repeat. Reliable agent systems may therefore need mechanisms such as:

  • idempotency keys;
  • unique operation IDs;
  • deduplication records;
  • transactional writes;
  • read-before-retry checks;
  • tool-specific retry policies.

RFC 9110 uses the same underlying concept for idempotent HTTP request semantics and explains why idempotency matters when a client loses the response to a request.

The lesson

Automatic retry is a tool-specific policy, not a universal recovery strategy.

32

Concurrency creates consistency problems

Subagents and distributed workers can operate on shared state concurrently. That raises familiar questions:

  • In what order are updates committed?
  • Can two workers overwrite one another?
  • Can both claim the same task?
  • Which event stream is authoritative?
  • How are conflicting side effects detected?

Google’s Agent Executor explicitly calls out session consistency and uses architectural constraints to reduce corruption in distributed agent workflows [16].

The exact solution depends on the application. Some systems serialize writes. Others partition state by task or resource.

Key idea

Multi-agent concurrency is not only a prompting problem. It is also a state-consistency problem.

33

Subagents are a harness choice

A harness may assign one model instance the whole task. It may also delegate independent subtasks to additional agents.

Delegation can improve throughput when work decomposes cleanly. It can also create duplicated work, inconsistent assumptions, communication overhead, higher token cost, error propagation, and conflict over shared state.

Google Research evaluated 180 agent configurations and found that architecture effects depended strongly on task structure. In their reported setup, centralized coordination improved Finance-Agent performance by 80.9% relative to the single-agent baseline, while every tested multi-agent variant degraded performance on the sequential PlanCraft task by 39–70% [17].

Those are results from that experimental setup, not universal scaling laws.

Durable rule

Delegation should be justified by task decomposition, not by a belief that more agents are inherently better.

Part VII

System design and evaluation

34

Agent legibility

OpenAI uses the phrase agent legibility for an important property of agent-first engineering environments [10]. The basic idea is to make the information an agent needs discoverable from the systems it can inspect.

  • For a code repository, that may include structured documentation, predictable package boundaries, clear ownership, test entry points, searchable logs, local metrics, and runnable application state.
  • For a data system, it may mean discoverable schemas and metadata.
  • For UI work, it may mean screenshots, DOM state, and deterministic ways to launch the application.

This is more than documentation quality. A system can be easy for its original human authors to understand because they carry tribal knowledge that the agent does not have.

Key idea

Harness engineering pushes important assumptions into inspectable artifacts.

35

Mechanisms are stronger than prose for enforceable rules

Suppose an architecture rule says:

Domain A must not import internal implementation code from Domain B.

One option is to write that rule in an instruction file. Another is to implement a structural test that rejects the forbidden dependency.

The second changes the failure mode. The agent no longer needs to remember perfectly. The invalid state fails verification.

OpenAI reports using custom linters and structural tests to enforce architectural rules in its Codex-first repository [10].

Instructions remain useful because not every property can be formalized. But where a rule is objective and mechanically checkable, encoding it in code reduces dependence on model obedience.

36

Observability has two audiences

Traditional observability helps engineers understand running software. Agent systems add a second audience: the agent itself.

For human operatorsFor the agent
Model turns, tool calls, tool failures, latency, token use, cost, retries, approval events, final outcomesApplication logs, traces, screenshots, browser state, test results, resource state
Helps people debug the harnessGives the model evidence about the system it is working on

OpenAI’s Codex-first engineering work demonstrates this by exposing logs, metrics, and traces directly to coding agents [10].

37

Agent harness vs evaluation harness

An agent harness lets a model operate. An evaluation harness measures how the resulting system performs.

Anthropic describes an evaluation harness as infrastructure that runs tasks end-to-end, provisions stable environments, records trials, executes graders, and aggregates results [8].

Independent benchmarks reinforce why that environment matters. τ-bench evaluates tool-using agents against final database state and repeated-trial reliability [22]. ToolSandbox evaluates stateful tool use with implicit dependencies between tools, on-policy conversations, and intermediate/final milestones over arbitrary trajectories [23]. Together they make it harder for an agent to receive credit merely for producing a plausible transcript.

That distinction matters because an agent evaluation typically measures more than the model:

measured agent performance = F(model, harness, environment, task, grader)

This is not a statistical model; it is a reminder about dependency.

Source checkAnthropic’s exact definition: it runs evals end-to-end, provides instructions and tools, runs tasks concurrently, records all the steps, grades outputs, and aggregates results. Isolating environments per trial is separate advice in the same article.
Key idea

Changing the harness can change the result without changing the model weights. Changing the environment can do the same.

38

The environment can change the benchmark score

Static question-answer benchmarks mostly score model outputs. Agentic coding benchmarks can involve package installation, compilation, test execution, process spawning, disk use, CPU and memory pressure, and repeated tool interaction. That makes infrastructure part of the task.

Anthropic experimentally varied compute resources on Terminal-Bench 2.0 and reported a six-percentage-point difference between its least- and most-resourced configurations in its experiment (p < 0.01). The shape of the result matters:

  • From 1x through roughly 3x resource headroom, infrastructure failures fell substantially while success scores remained within statistical noise (p = 0.40).
  • Above roughly 3x, additional resources began enabling strategies that materially changed task success.

Anthropic therefore recommends skepticism toward leaderboard gaps below three percentage points when resource methodology is not documented and matched [9].

The correct conclusion is not: “More RAM makes the model smarter.” It is:

Key idea

An agentic benchmark can measure interactions between model behavior and runtime resources.

Meaningful comparison therefore requires enough detail about the harness and environment to reproduce the operating conditions.

39

Harness assumptions can expire

A harness often contains workarounds for known model behavior. Those workarounds should not be assumed permanent.

Anthropic reports that context-reset machinery added because Claude Sonnet 4.5 could prematurely wrap up work near its context limit became unnecessary when the same harness was used with Claude Opus 4.5. The behavior had changed, so the reset became dead weight.

In the same set of experiments, Anthropic reports a specific RetroForge comparison in which a solo Opus 4.5 run lasted 20 minutes and cost $9, while the fuller harness ran for six hours and cost $200. The author reports that the fuller harness produced substantially better output quality in that experiment, but it was more than 20x as expensive. Later experiments with Opus 4.6 removed additional scaffolding, including the sprint decomposition. The planner remained useful, while the evaluator became more task-dependent: it added the most value when the task sat near the model’s capability edge. These are task-specific experiments, not universal cost ratios [11].

OpenAI’s current Agents API likewise treats the Codex harness as a versioned system that evolves alongside model capabilities [20].

A stronger design principle

Every harness component is a hypothesis about a current limitation, and it should justify both its quality lift and its execution cost for the model and task distribution being served.

When the model changes, test that hypothesis again. Otherwise harnesses accumulate obsolete layers that add latency, token cost, complexity, and new failure modes.

Part VIII

Synthesis: failures, misconceptions, and the mental model

40

Common failure modes

A production harness should make failures observable and classifiable.

Tool-selection failureThe capability exists, but the model chooses the wrong tool.
Tool-contract failureThe intended tool is correct, but arguments are invalid.
Observation failureThe action succeeds, but the returned information is noisy, ambiguous, or incomplete.
Context failureImportant information is omitted, stale, buried, or destroyed during compaction.
State failureThe system loses track of progress, approvals, plans, or prior actions.
Environment failurePackages, files, browser state, compute resources, or permissions differ from assumptions.
Verification failureThe model declares success without testing the external result.
Authorization failureThe agent is either blocked from legitimate work or granted more authority than needed.
Recovery failureA retry duplicates a side effect or a restart cannot reconcile control state with world state.
Coordination failureSubagents duplicate work, diverge in assumptions, or spend more resources coordinating than solving the task.
Budget failureThe run consumes its allowed turns, time, tokens, cost, or concurrency before reaching a successful terminal state.
Provenance / prompt-injection failureUntrusted tool data, retrieved content, stored state, skills, or subagent output is treated as authoritative instruction and redirects the agent [3,21].
Skill-induced failureA loaded skill is topically relevant but causes required work to be implemented incorrectly or omitted, or adds enough unnecessary procedure to create a material efficiency regression [24].
Key idea

Harness engineering is largely the work of turning these broad failure categories into observable, testable system properties.

41

Common misconceptions

Click each statement to reveal the correction.

“The harness is the system prompt.”

No. Instructions are one part of a harness. The harness can also own state, tool dispatch, approvals, compaction, recovery, budgets, and verification.

“The harness is the sandbox.”

No. The harness controls work; the sandbox is one place where work executes [14].

“MCP is the agent.”

No. MCP standardizes interoperable capability surfaces and extensions. The agent loop and its policies still require orchestration [13].

“Context window equals memory.”

No. Durable state can exist outside the current model context.

“Compaction preserves the full conversation.”

No. A summary is a lossy representation unless omitted information remains recoverable elsewhere.

“More tools always improve capability.”

No. Overlap and noisy results can make selection and downstream reasoning harder.

“A human approval prompt makes arbitrary execution safe.”

No. Approval and environmental containment solve different problems.

“If a tool failed, retry it.”

Not automatically. Side-effecting operations may need idempotency or deduplication semantics.

“The agent said it finished, so the task is complete.”

No. Self-report is weaker than observable verification.

“More agents are better.”

Not generally. Coordination cost can dominate on tightly sequential work [17].

“A better model makes every old harness improvement useful.”

No. Scaffolding can become unnecessary as model behavior changes [11].

“Skills are just harmless prompt templates.”

No. Skills can contain instructions, resources, and executable scripts. Third-party skills should be treated as provenance-bearing code/configuration and reviewed, sandboxed, and approval-gated according to the capabilities they expose [25,26].

42

A production mental model

When evaluating an agent system, ask:

#QuestionPossible answers
1What does the model actually receive?Instructions, history, tool schemas, retrieved state, summaries, artifacts.
2Who controls the loop?Application code, a managed harness, a workflow engine, or another agent.
3What actions are available?Function tools, MCP tools, shell, browser, files, APIs, subagents.
4Where do actions execute?Trusted process, local machine, container, VM, remote service.
5What survives the next turn or process crash?Session events, files, snapshots, external side effects.
6Which rules are enforced mechanically?Schemas, mounts, network boundaries, approvals, tests, budgets.
7How are errors represented?Fatal exception, retry, model-visible observation, human escalation.
8Which actions are safe to retry?Idempotent operations, deduplicated operations, or neither.
9How does the agent obtain ground truth?Tests, logs, browser state, database state, external responses.
10What proves completion?A model claim, deterministic validator, external state, evaluator, or human.
11How does the run stop if it never succeeds?Turn, time, token, tool, cost, or policy budgets.
12What happens after interruption?Resume, retry, reprovision, rollback, or restart.
13Can untrusted observations carry instructions?Web data, tool output, files, memory, loaded skills, subagent reports.
14How are subagents coordinated?Task boundaries, shared state, merge policy, concurrency limits.
15How is the harness evaluated?Ablations, representative tasks, stable environments, outcome metrics.

A system that cannot answer these questions may still work in a demo. It is much harder to reason about in production.

43

The complete mental model

A compact production picture is:

The modelsupplies learned capability.
The harnessdecides how that capability is connected to work.
The persistent session/state layerdetermines what can survive across turns or restarts.
The context policydetermines what the model can see now.
The execution environmentdetermines what can actually happen.
Permissions and containmentdetermine what failure can reach.
Feedbacktells the system whether an action worked.
Verificationdetermines whether “done” is evidence-backed.
Recoverydetermines whether work can continue after interruption.
Evaluationdetermines whether the harness is helping rather than merely adding machinery.
Closing

That is the core of harness engineering.

B1

Best practices: tool and interface design

Extends sections 05–10

  1. Consolidate tools around workflows instead of wrapping every endpoint. For example, replace list_users + list_events + create_event with a single schedule_event, and offer search_logs instead of read_logs. Anthropic · Tools
  2. Namespace tools, and measure prefix versus suffix. For example asana_search, jira_search. Anthropic found that the choice between prefix and suffix naming had a non-trivial effect on eval results, so test both. Anthropic · Tools
  3. Write tool descriptions like a docstring for a new developer. Use unambiguous parameter names (user_id, not user). Include examples, edge cases, input formats, and boundaries with other tools. Anthropic · Agents
  4. Poka-yoke your parameters so they are hard to misuse. Anthropic’s SWE-bench agent kept failing with relative paths; requiring absolute paths removed the problem. Prefer formats close to natural text, and avoid making the model count lines or escape strings. Anthropic · Agents
  5. Return meaningful fields instead of technical IDs. Prefer name, image_url, file_type over uuid, 256px_image_url, mime_type. Anthropic · Tools
  6. Add a response_format: "concise" | "detailed" parameter. In Anthropic’s example the concise response took 72 tokens and the detailed one 206; the agent picks the level it needs. Anthropic · Tools
  7. Cap output, and when you truncate, explain how to get more. Claude Code caps tool results at 25,000 tokens. SWE-agent caps search at 50 results and its file viewer at 100 lines. A 30-line viewer scored only 14.3% and a whole-file view 12.7%, versus 18% with 100 lines. SWE-agent
  8. Lint on edit, and reject edits that break syntax. Removing the linter dropped SWE-agent from 18.0% to 15.0%. SWE-agent
  9. Send tool errors back to the model so it can correct itself. Set toolNotFoundBehavior: 'return_error_to_model' (the default is 'raise_error') and write domain-aware messages with toolErrorFormatter. Validation errors should include an example of correct input. OpenAI · Agents SDK
  10. Improve tools with evals and transcripts. Build a few dozen realistic tasks that need many tool calls. Track runtime, tool-call count, tokens, and error rate. Read the raw transcripts, then hand them to the agent itself to analyze and fix the tools. Anthropic · Tools
B2

Best practices: context, instructions, and skills

Extends sections 12–15

  1. Keep AGENTS.md around 100 lines, as a table of contents. It points to ARCHITECTURE.md and a structured docs/ directory (design-docs, exec-plans, product-specs, references, generated/db-schema.md). As OpenAI puts it: “When everything is ‘important,’ nothing is.” OpenAI · Harness eng.
  2. Write the system prompt at the right altitude. Avoid both brittle hard-coded logic and vague guidance. Use clear sections (<background_information>, <instructions>, ## Tool guidance) and a few diverse, canonical few-shot examples instead of listing every edge case. Anthropic · Context
  3. Load context just in time through lightweight identifiers. Keep file paths, queries, or links in context, and load content with tools when needed. Claude Code combines both approaches: CLAUDE.md up front, the rest discovered with glob and grep. Anthropic · Context
  4. When compacting, keep architectural decisions, unresolved bugs, and implementation details. The safest first step is clearing old tool results deep in the history. Anthropic · Context
  5. Let the agent take notes in a file. Use something like NOTES.md or a file-based memory tool, read back after each context reset. In the Pokémon example, notes let the agent keep its progress across thousands of steps. Anthropic · Context
  6. Have subagents return condensed summaries of about 1,000–2,000 tokens. A subagent can spend tens of thousands of tokens exploring, but the lead agent only needs the distilled result. Anthropic · Context
  7. Advertise each skill in about 100 tokens and keep its body under 5,000. Separate mandatory requirements from examples and templates, so the agent does not treat general guidance as an obligation. In the skills paper, 67 failures came from excessive verification. Microsoft · Skills Skills paper
B3

Best practices: long-running agents and working state

Extends sections 17 and 29

  1. Split an initializer agent from the coding agent. The first session only lays the foundation: feature_list.json, claude-progress.txt, init.sh, and a git repo. Later sessions make incremental progress. Anthropic · Long-running
  2. Keep the feature list in JSON, not Markdown. Each feature defaults to "passes": false. Anthropic found the model is less likely to inappropriately change or overwrite JSON than Markdown. Anthropic · Long-running
  3. Give every session a fixed start-up ritual. Run pwd, read the git log and progress file, read the feature list, run init.sh, then run a basic test to catch leftover breakage before writing new code. Anthropic · Long-running
  4. Work on one feature per session and end in a clean state. Commit with a descriptive message and update the progress notes, as if handing off to the next shift’s engineer who has no memory. Anthropic · Long-running
  5. Forbid editing or deleting tests in the prompt itself. Anthropic’s wording: “It is unacceptable to remove or edit tests…”. Anthropic · Long-running
  6. Treat the harness as cattle, not a pet. The session is an append-only log outside the harness. When the harness crashes: wake(sessionId) → getSession(id) → resume from the last event. Every “hand” goes through one interface, execute(name, input) → string. Anthropic · Managed Agents
  7. Know the difference between manifest, snapshot, and RunState when resuming. RunState restores harness-side state (approvals, agent position). A snapshot seeds a workspace. Credentials are runtime configuration and stay out of the prompt. OpenAI · Sandboxes
B4

Best practices: verification, feedback, and legibility

Extends sections 25–28 and 34–36

  1. Test end-to-end the way a real user would. Use browser automation (Puppeteer MCP, Playwright) and mark a feature passing only after testing. Note that the agent cannot see native browser alert modals. Anthropic · Long-running
  2. Use a separate, skeptical evaluator. An agent grading its own work tends to praise it confidently even when quality is mediocre. Define clear grading criteria and calibrate the evaluator with few-shot examples and detailed scores. Anthropic · Harness design
  3. Agree on a “sprint contract” before coding. The generator and evaluator agree on what “done” means for each chunk, and communicate through files. Anthropic · Harness design
  4. Boot an app instance per git worktree. Wire in the Chrome DevTools Protocol so the agent can take DOM snapshots and screenshots. Tear the instance down when the task finishes. OpenAI · Harness eng.
  5. Give the agent a local observability stack. Route logs, metrics, and traces through Vector into Victoria Logs/Metrics/Traces, queried with LogQL/PromQL/TraceQL. Only then can a requirement like “startup under 800ms” be verified. OpenAI · Harness eng.
  6. Put remediation instructions in lint error messages. Lint output goes straight into the agent’s context, so write the fix into the message. Enforce fixed layers: Types → Config → Repo → Service → Runtime → UI. OpenAI · Harness eng.
  7. Run garbage-collection and doc-gardening agents on a schedule. Write down “golden principles” and let background agents find drift and open small PRs. Manual cleanup used to take every Friday, 20% of the week. OpenAI · Harness eng.
B5

Best practices: security and containment

Extends sections 18–22

  1. Sandbox at the OS level: read anywhere, write only in the workspace, network off by default. Use Seatbelt on macOS, bubblewrap on Linux, or a VM with its own kernel. This cut permission prompts by 84%. Anthropic · Containment
  2. Never put credentials in the sandbox. Attach the git token to the remote at init time. Route MCP calls through a proxy that fetches secrets from a vault, so the agent never touches a token. Anthropic · Managed Agents
  3. Treat every domain on an egress allowlist as a granted capability. Every API behind that domain becomes attack surface. Use a proxy that only passes the session’s own token (the lesson of the api.anthropic.com incident). Anthropic · Containment
  4. Do not trust subagent output more than raw tool results. Doing so opens a new prompt-injection channel. Anthropic · Containment
  5. Enable only the tools a task needs. In AgentDojo, tool filtering was the most effective defense. It still fails when the user task and the attacker’s task need the same kind of tool. AgentDojo
  6. Vet skills like third-party dependencies. Read the whole SKILL.md and its scripts, run scripts in a sandbox, and log which skills load. Always keep approval on run_skill_script; read-only actions can be auto-approved. Microsoft · Skills
  7. Layer your guardrails. Input guardrails run only on the first agent and output guardrails only on the last. Tool guardrails return allow, rejectContent, or throwException, and do not apply to handoffs. Set runInParallel: false to block before the model call. OpenAI · Guardrails
B6

Best practices: loop control, retries, and recovery

Extends sections 23–24 and 30–32

  1. Always set maxTurns, and handle hitting it. The default is 10. Use errorHandlers (maxTurns, modelRefusal, invalidFinalOutput) to turn errors into output with an explicit status, not a generic “done”. OpenAI · Agents SDK
  2. Automatically retry only idempotent operations. RFC 9110 allows automatic retry only for idempotent methods when the response is lost. For create_* or charge_*, use an idempotency key or read the state before retrying. RFC 9110
  3. Persist task IDs durably and respect pollIntervalMs and ttlMs. Distinguish isError: true (the task is still “completed”) from JSON-RPC errors (“failed”). Task IDs need enough entropy, and every task request must be authorized. MCP Tasks
  4. Use a single-writer architecture for shared sessions. Combine an event log and snapshots to resume without corrupting state. Google · Agent Executor
  5. Use checkpointed workflows when execution order must be guaranteed. On failure they resume from the last checkpoint instead of starting over. Microsoft · Workflows
Backend note: this list is close to the checklist for a payment pipeline or message queue: at-least-once delivery with dedup, the outbox pattern, single writer per partition. Distributed-systems experience transfers directly.
B7

Best practices: when to go multi-agent

Extends section 33

  1. Start simple. A single LLM call with retrieval is often enough. When the path is known, use workflow patterns: prompt chaining with gates, routing (easy questions to a small model, hard ones to a large model), parallelization, orchestrator-workers, evaluator-optimizer. Reach for an agent only when the number of steps cannot be predicted. Anthropic · Agents
  2. Use a single agent for sequential tasks. On PlanCraft, every multi-agent variant was 39–70% worse. Google Research
  3. If you go multi-agent, prefer centralized coordination. Errors amplify 4.4x with centralized coordination, versus 17.2x with independent agents. Google Research
  4. Account for the coordination tax on tool-heavy agents. At around 16 or more tools, the cost of coordinating multiple agents grows disproportionately. The study’s predictive model picked the right architecture for 87% of held-out configurations. Google Research
B8

Best practices: evaluating and shipping harness changes

Extends sections 16 and 37–39

  1. Start with 20–50 tasks drawn from real failures. Turn manual checks and real bugs into automated tasks. A good task is one where two domain experts would independently reach the same pass/fail verdict. A 0% pass rate across many trials usually means the task is broken. Anthropic · Evals
  2. Pick the right metric: pass@k or pass^k. pass@k means at least one of k tries succeeds; pass^k means all k do. At 75% per trial, pass^3 = 0.75³ ≈ 42%. Use pass^k when you need consistency. Anthropic · Evals
  3. Combine three kinds of grader. Code-based graders are fast and cheap but brittle. LLM judges are flexible but need calibration against experts and should be allowed to answer “Unknown”. Human graders are the gold standard but expensive. Anthropic · Evals
  4. Grade outcomes, not paths, and read transcripts often. Opus 4.5’s CORE-Bench score rose from 42% to 95% just by fixing an overly strict grader that rejected “96.12” because it demanded “96.124991…”. Anthropic · Evals
  5. Separate capability evals from regression evals. Capability evals start at a low pass rate, a hill to climb. Regression evals stay near 100%. When a capability eval saturates, graduate it into the regression suite. Anthropic · Evals
  6. Isolate every trial’s environment. In one case an agent read a previous trial’s git history and gained an unfair advantage. Anthropic · Evals
  7. Specify resources with two parameters: a guaranteed level and a kill threshold. Anthropic uses a 3x ceiling over the spec. Treat infrastructure configuration as an experimental variable, controlled as tightly as temperature. Anthropic · Infra noise
  8. Run a broad per-model eval suite for every system-prompt change. Ablate prompt lines one at a time. Have staff use the exact public build, add a soak period, and roll out gradually. These were Anthropic’s commitments after the April postmortem. Anthropic · Postmortem
  9. Remove scaffolding as models improve. “Every component in a harness encodes an assumption about what the model can’t do.” Keep an evaluator only when the task is beyond what the model does reliably on its own. Anthropic · Harness design

Self-check, key terms, and references

Q

15 self-check questions

Based on the “by the end you should be able to explain” list. Answer first, then click to reveal.

Q1Why is a single model call not yet an agent?
Because y ~ p_θ(·|c) only produces output. Nothing runs commands, observes results, or keeps working. An agent needs an external control process (the harness) that puts that output into a controlled interaction loop with external state. §01
Q2Describe the minimal agent loop using s, c, a, o.
c_t = G(s_t) selects context; a_t = M(c_t) the model produces an action; o_t = E(a_t) the environment returns an observation; s_(t+1) = U(s_t, a_t, o_t) updates state. Repeat until a final output or a stopping condition. §02
Q3How do the harness and sandbox differ, and why separate them?
The harness is the control plane (context selection, tool routing, approvals, recovery). The sandbox is the execution plane (runs code, edits files). Separating them keeps untrusted code in the sandbox away from session state, audit logs, credentials, and policy. §19
Q4What are the four properties for analyzing a tool?
Affordance (what it can do), Contract (how it is requested), Observation (what comes back), Feedback (whether the next correct step gets easier). §06
Q5Why can adding tools make an agent worse?
Every tool lands in context and widens the action space. Overlapping tools raise C_selection; noisy results raise C_observation. Tool count is not a monotonic measure of capability. §07, §08
Q6What does MCP not decide?
Loop scheduling, context selection, completion criteria, which actions need approval, retrying side effects, sandbox provisioning, multi-agent coordination, and agent evaluation. MCP is a capability interface, not an agent architecture. §11
Q7How does active context differ from durable state?
Durable state is the stored history/state (for example an append-only session log); active context is what gets selected into one call. They overlap, but neither contains the other. §14
Q8Why is compaction lossy, and how should you design for it?
C(H) ≠ H: a summary can drop details a later step needs. Keep durable history separately and give the agent a way to retrieve what was omitted. §15
Q9How do approval, containment, and credential isolation differ?
Approval controls decisions but suffers approval fatigue (about 93% approved). Containment controls what can be reached even if every other layer fails. A credential that never enters the sandbox cannot be read from it. §20, §21
Q10What does a model-usable tool error look like?
Structured: status, reason, the requested parameters, valid alternatives, side_effects, retryable. Enough to choose a better next action, without pretending the call succeeded. §10
Q11Why is retrying create_ticket dangerous?
If the ticket was created but the response was lost, a retry creates a duplicate. You need idempotency keys, operation IDs, dedup records, or read-before-retry. Retry is a per-tool policy. §30, §31
Q12Why separate verification from self-reported completion?
“The bug is fixed” is a claim, not evidence. Tie completion to observable state (tests pass, DB state matches the goal as in τ-bench). Also keep “complete” distinct from “budget exhausted”. §23, §25
Q13When do subagents help, and when do they hurt?
They help when the task decomposes cleanly (Finance-Agent +80.9% with centralized coordination). They hurt on tightly sequential work (PlanCraft −39% to −70%). Delegate based on decomposability. §33
Q14What does an agent evaluation actually measure?
F(model, harness, environment, task, grader). Changing the harness or resources (Terminal-Bench: a 6-point gap) can change scores without changing weights. §37, §38
Q15Why retest the harness when models improve?
Each component is a hypothesis about a current limitation. The context reset needed for Sonnet 4.5 became dead weight with Opus 4.5. Without retesting, harnesses pile up obsolete layers that cost latency and tokens and add new failure modes. §39
G

Key terms

agent harness
The runtime and control machinery around a model that lets it act over multiple steps.
harness engineering
The discipline of designing interfaces, context, state, environment, controls, feedback, recovery, and verification for agentic work.
control plane / execution plane
The layer that decides (harness) / the layer that executes (sandbox).
active context
The information supplied to one specific model call.
durable state / session
History and state stored durably, surviving turns and crashes.
compaction
Replacing older detail with a summary to save context; lossy.
progressive disclosure
Give enough to orient, make depth discoverable, load detail on demand.
ACI
Agent-Computer Interface: the interface an agent uses to operate a computer.
affordance
The operation a tool makes possible.
provenance
Where an observation came from, which determines its trust and authority.
prompt injection
Malicious instructions planted in data (web, tool output, files) to steer an agent.
containment
Environment-level limits on what an agent can reach.
egress
Outbound network traffic.
approval fatigue
Users approving prompts reflexively because they see too many.
idempotent
Repeating it has the same effect as doing it once: f(f(s)) = f(s).
side effect
A change to external state (sending email, charging a card, creating a record).
guardrail
An input, output, or tool check that can validate or block execution.
pass@1 / pass^k
Success on the first try / success on all k tries.
agent legibility
How discoverable the information an agent needs is from the system itself.
evaluation harness
Infrastructure that runs tasks end-to-end, grades them, and aggregates results.
ablation
Removing one component at a time to measure its contribution.
