Harness Engineering

A harness is the infrastructure around your code that decides whether it can be trusted. For human-written code that means test infrastructure; for AI-written code it also means mechanical guardrails that constrain and correct an agent in real time.

Core principles

Grow it incrementally

Nobody builds a complete harness up front. Add one test, one lint rule, one hook at a time, in response to a real gap. Big-bang harness projects get abandoned.

Isolation first

Every test, agent run and pipeline stage must produce the same result regardless of what ran before it.

Determinism over speed

Same inputs, same outputs. Freeze the clock, seed the RNG, stub the network.

Observability

A failure should hand you the answer, not a puzzle: inputs, logs, stack trace and, for agents, the exact tool calls and results.

Mechanical enforcement beats prose

"Write good code" in an instruction file does nothing measurable. A linter rule, type check or blocking hook does.

Close the loop

Feed the output of a check (test, lint, type error) straight back to the agent in the same turn so it can self-correct.

Sanity-check checklist

  • Can a new test, rule or hook be added without touching unrelated ones?
  • Does anything depend on execution order, shared mutable state or leftover data?
  • Is there wall-clock time, a live network call or unseeded randomness in the critical path?
  • Does a failure hand you a root cause or a mystery?
  • Do stubs exercise failure modes, not just the happy path?
  • Is there a plan to catch stub drift?
  • Does the agent instruction file stay under ~50 lines and point elsewhere for detail?
  • Do lint and type errors say what to do, not just what is wrong?
  • Are flaky checks quarantined and fixed fast, not "just rerun"?
Treat the harness as production code: review it, test it, and fix or quarantine flakiness immediately. A harness that produces false failures quickly loses the team's trust.
