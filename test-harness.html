Test Harness Fundamentals

A test harness is everything surrounding the code under test: fixtures, mocks and stubs, the runner and the environment. Its job is to make "does this work?" answerable automatically and identically every time.

Isolation first

  • No shared mutable global state between tests.
  • No test that depends on another having run, or having run first.
  • Reset fixtures (database rows, temp files, caches) before or after each test, not just at suite start.
  • For parallel runs, shared ports, temp directories and database rows are the most common source of "flaky" failures that are really races.

Determinism over speed

A fast but non-deterministic harness trains the team to ignore red builds. Eliminate:

  • Wall-clock time: inject a clock instead of calling now().
  • Unseeded randomness: seed the RNG and log the seed on failure.
  • Real network calls: put live third-party services behind stubs.
  • Unordered collections: sort before asserting.
  • Concurrency: a race that shows up 1 in 50 runs is still a bug; do not paper over it with retries.

Drivers vs. stubs

Driver

Simulates a higher-level caller (CLI, UI, calling service) so you can test a module before its real caller exists.

Stub

Simulates a lower-level dependency (database, payment API, queue) so you can test without it running.

Stub failure modes, not just success

A stub that only returns the happy path tests nothing about resilience. At minimum simulate:

  • Timeouts and slow responses
  • Connection refused and DNS failure
  • 4xx errors: bad request, auth failure, rate limiting
  • 5xx errors: dependency down, partial outage
  • Malformed or unexpected-shape responses
  • Declined business outcomes, e.g. a declined payment

The stub drift trap

Stubs are frozen assumptions. Real APIs add fields, change error codes and evolve, so a suite can stay green for months while production breaks.

Mitigations
  • Run a subset of integration tests against the real dependency (or a faithful sandbox) on a schedule, e.g. nightly.
  • Generate stubs from the real contract (OpenAPI, protobuf, GraphQL schema) so drift shows up as a diff.
  • Treat "the stub needs updating" as a first-class finding; never just delete the failing integration test.

Observability on failure

Capture and surface: the actual inputs (including the random seed), logs at the point of failure, the full stack trace, and any network activity the stub observed (what was called, with what, how many times).

Growing the harness incrementally

  • Add the mock or fixture you need for the test you are writing now.
  • Extract shared setup only after you see duplication in 2-3 tests.
  • Review harness code with the same rigor as production code.
  • Quarantine flaky tests immediately (mark, ticket, fix or delete on a deadline).
